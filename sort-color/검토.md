# Color Sort Platform Notes 검토 보고서

해당 문서(`color-sort-platform-notes.md`)를 면밀히 검토했습니다. 이 문서는 현재 단일 `Cardioid` 기하학(Geometry)에 강하게 결합된 `sort-color` 프로젝트를 **`기하학(Geometry) x 색상 키(Color Key) x 정렬 알고리즘(Sort Algorithm)`** 의 3축 조합이 가능한 **범용 정렬 시각화 플랫폼(Color-based Sorting Platform)** 으로 확장하기 위한 훌륭하고 체계적인 아키텍처 설계도입니다.

검토 내용을 바탕으로 실행 난이도, 문제점 및 핵심 개선사항을 정리해 드립니다.

---

### 1. 실행의 난이도: **중상 (Medium-High)**
문서에서도 언급되었듯, 이 작업은 단순히 기능을 추가하는 것이 아니라 시스템의 근간을 4개의 독립된 계층으로 쪼개는 **대규모 리팩터링(Refactoring)** 입니다. 

* **기반 구조 분리 (난이도: 중간):** Cardioid 수식과 정렬 알고리즘, 렌더링 로직을 분리해 인터페이스화하는 작업은 코드 이동과 캡슐화를 통해 안전하게 달성할 수 있습니다.
* **새로운 Geometry/Algorithm 추가 (난이도: 중간):** 구조만 잘 분리된다면, Sphere나 Grid를 추가하거나 Merge Sort 등을 추가하는 것은 플러그인처럼 쉽게 붙일 수 있습니다.
* **비교 모드 (Compare Mode) (난이도: 중상~높음):** 두 개의 각기 다른 정렬/기하학 실험을 동시에 띄우고 상태 관리와 재생(Playback) 동기화(Linked Transport)를 맞추는 작업은 상태 관리의 복잡도를 크게 높이므로 난이도가 높습니다.

### 2. 현재 구조의 문제점 (강한 결합도)
현재 프로젝트가 범용화되기 위해 겪고 있는 가장 큰 기술적 한계(부채)는 다음과 같습니다.
1. **정렬과 기하학의 혼재:** 정렬 로직과 렌더링 로직 내부에 Cardioid를 그리기 위한 수학적 수식(`multiplier`, `pointCount`, Chord 계산 등)이 하드코딩되어 강하게 묶여 있습니다.
2. **색상 추출 로직 파편화:** 색상(Color) 기준을 추출하고 정렬 계획을 세우는 코드가 알고리즘(Radix, Bubble, Quick) 내부나 주변부에 흩어져 있습니다.
3. **공통 인터페이스 부재:** 각 정렬 알고리즘이 발생시키는 이벤트 단계(Plan)들이 규격화되지 않아, 렌더러가 각 알고리즘의 특이 케이스(예외 상황)를 너무 많이 알아야 합니다.
4. **확장의 병목:** 현재 구조에서는 레이아웃(Sphere, Grid)을 추가하려고 할 때마다 기존 정렬 렌더러와 엔진을 전부 수정해야 하는 충돌 위험이 존재합니다.

### 3. 구조적 개선사항 (4대 핵심 추상화 계층 도입)
문서가 제시하는 방향대로 기능을 철저히 분리(Decoupling)하는 것이 가장 큰 개선사항입니다.

* **Geometry Provider:** 기하학적 형태는 '정렬 방법'을 전혀 몰라야 합니다. 오직 슬롯(좌표) 목록과 공간적 메타데이터(Face center, Adjacency 등)만 제공하도록 분리해야 합니다.
* **Color Key Extractor:** Geometry에서 항목 전체를 가져오지 않고, 정렬의 기준이 되는 순수 키값 (Hue, RGB, HSL 스칼라 값 등)만 독립적으로 추출하는 계층을 둬야 합니다.
* **Sort Planner (Engine):** 시각적 요소(도형)는 배제하고 입력된 키값과 알고리즘에 따른 '정렬 단계(Step/Event) 실행 계획'만 생산하는 공통 인터페이스가 필요합니다.
* **Sort Renderer:** 정렬 알고리즘 내부를 알 필요 없이, Planner가 준 '현재 활성화된 인덱스, 피벗 등'의 상태 메타데이터만 받아 해당 좌표(Geometry)에 색상을 입혀 그리기만 하도록 책임을 축소해야 합니다.

### 4. UI 역할의 명확한 재정의
현재의 UI를 범용 플랫폼에 맞게 동적으로 구성해야 합니다. (`caustics` 프로젝트의 패턴 응용)
* **Top Menu:** 전역 선택 (Geometry 종류, Color Key 선택 등)
* **Left Panel:** 정렬 제어판 유지 (고정 영역 - 정렬 방식, 속도, Play/Hold/Step 컨트롤)
* **Right Panel:** 기하학 인스펙터 (동적 영역 - Cardioid의 N/M, Sphere의 면 분할 수 등 선택된 도형에 따라 UI가 동적 렌더링되도록 개선)

### 💡 실행을 위한 제언 (Recommended Action Plan)
절대 한 번에 갈아엎거나 시작부터 `Sphere` 모델을 같이 만들면 안 됩니다. 문서의 계획이 매우 훌륭하며 다음 순서를 강제하는 것이 안전합니다.

1. **Cardioid 의존성 뽑아내기 (Boundary Lock & Provider Split):** 현재 동작하는 앱을 깨지 않으면서 `cardioid_circle` 계열 파일들에서 기하학 수식만 빼내어 `Geometry Provider`로 캡슐화합니다.
2. **단일 공통 인터페이스화:** Radix, Bubble, Quick 정렬이 렌더러에게 전달하는 데이터를 통일합니다. 색상 기준도 `Color Key Extractor` 패키지로 뺍니다.
3. **Cardioid 플러그인 검증:** 기존 코드가 잘 쪼개져서 플러그인 모듈처럼 끼워졌을 때 현재와 똑같이 도는지 테스트합니다.
4. **새 프레임워크 분리 및 Sphere 추가:** 1~3이 성공하면 코드를 `sort-sphere` 등으로 파생(Clone) 시킨 후, `maze-art`의 `Goldberg Sphere`를 Prototype 계층으로 교체 투입합니다.
5. **Compare 모드 연기:** 병렬 비교 기능은 위 아키텍처가 완전히 자리 잡은 이후의 Phase 2 과제로 미루는 것이 좋습니다.
